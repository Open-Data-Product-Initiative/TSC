# 1. Establish OpenDataProducts.org as a family of data product standards

The maintainer proposes that OpenDataProducts.org evolves from the home of one specification into the home of a modular family of standards for data product management.

The current Open Data Product Specification, ODPS, remains focused on defining one data product. This focus should be preserved.

The proposed standards family adds two new specifications:

* Open Data Product Catalogs, ODPC
* Open Data Product Graphs, ODPG

Each specification can be used independently. Used together, they form a machine-readable operating model for managing data products, use cases, business objectives, KPIs, and signals.

The guiding principle is:

* ODPS defines the product.
* ODPC defines reusable portfolio objects.
* ODPG defines the relationships.

# 2. Initiate Open Data Product Catalogs, ODPC

ODPC will define the reusable portfolio objects needed for data product management.

The first draft scope includes:

* ProductReference
* UseCase
* BusinessObjective
* KPI
* Signal
* Catalog
* CatalogItem

ODPC will be ODPS-native, but not ODPS-only.

This means ODPC will support ODPS as the preferred product definition model, while also allowing references to other data product models such as DPDS, internal enterprise schemas, vendor catalog assets, and marketplace definitions.

This is important because many organizations already use existing product descriptions. ODPC should allow them to participate through explicit references and mapping profiles instead of forcing immediate migration to ODPS.

# 3. Initiate Open Data Product Graphs, ODPG

ODPG will define how cataloged objects are connected.

The first draft scope includes:

* Graph
* Node
* Edge
* RelationshipType
* Evidence
* Confidence
* Weight

ODPG should not redefine products, use cases, objectives, KPIs, or signals. It should reference objects defined in ODPC and product definitions from ODPS or external product models.

Example relationships include:

* UseCase USES DataProduct
* UseCase SUPPORTS BusinessObjective
* DataProduct CONTRIBUTES_TO BusinessObjective
* BusinessObjective MEASURED_BY KPI
* Signal SUGGESTS UseCase
* DataProduct DEPENDS_ON DataProduct

ODPC should be developed first because ODPG needs stable catalog object references.

# Proposed Decision

The TSC approves the direction to evolve OpenDataProducts.org into a family of modular standards:

* Open Data Product Specification, ODPS, lead Jarkko Moilanen
* Open Data Product Catalogs, ODPC. lead Jarkko Moilanen
* Open Data Product Graphs, ODPG, lead Zaher Abou Shakra

The TSC approves starting draft work on ODPC and ODPG.

The first phase will focus on:

* Defining the scope boundaries between ODPS, ODPC, and ODPG
* Creating a ProductReference model
* Creating draft object models for UseCase, BusinessObjective, KPI, Signal, Catalog, Node, and Edge
* Creating examples that show ODPS-native usage
* Creating examples that show non-ODPS product references, including DPDS
* Preparing draft schemas and reference examples for community review

**DECISION**

* The TSC approves initiating ODPC and ODPG as separate but related specifications under OpenDataProducts.org.
* ODPC will be developed first as the reusable portfolio object specification.
* ODPG will be developed after the first ODPC object model draft is stable enough to reference.
* Both ODPC and ODPG will be designed as ODPS-native, but not ODPS-only. They will support external product models through ProductReference and mapping profiles.

The maintainers will prepare initial draft scope documents, object models, and examples for TSC and community review.
